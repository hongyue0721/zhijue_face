# 施工计划、依赖、演示与计划书衔接

## 1. 不是“一次性让 AI 写完整个平台”

工作以纵向可运行切片推进。每个里程碑先定义验收，随后实现、测试和同步文档；未通过前置门槛，不并行堆后续页面。工作量是规划估算，实际由 M0 实测和个人有效投入校正，不承诺自动完成或固定工期。

| 阶段 | 任务 | 前置 | 必须看得见的结果 | 估算有效工时 |
|---|---|---|---|---:|
| M0 | 环境、规则与真实框架验证 | 无 | SDK/模型/Knowledge 可用，精确依赖锁定；规则待确认清单 | 4—6 |
| M1 | 资料、事实与确认闭环 | M0 技术通过 | 原件→分块→声明→人工确认→知识库激活；可找回引用 | 6—8 |
| M2 | 五题计划和出题 | M1 | 6 条审核种子先跑通；换简历仍能产生有依据的问题 | 6—8 |
| M3 | 一问一答、有界策略与恢复 | M2 | 模糊回答追问、充分回答换题；刷新不重扣费、不重复推进 | 8—10 |
| M4 | 评分、改写、简历入口 | M3 | 根题合并评分、引用可查、简历差异确认及打印 | 5—7 |
| M5 | 集成验收、评测、演示资料 | M4 | P0 用例报告、已知失败、真实演示、提交物检查 | 6—8 |

合计约 35—47 小时的有效工程投入，另外保留缓冲；不包含等候校方答复、找审核人、账号申请。工时是人和 AI 协作的任务预算，不是本助手承诺在后台完成的时间。

按 9 月 18 日启动的目标：9 月 23 日冻结核心、24 日整理演示和材料。全国报名及对策提交截止是 2026 年 9 月 25 日 12 时，校内窗口另核。[S02] 若校内更早截止，优先交如实描述进度的材料，不把未来能力写成已实现。

## 3. 依赖和暂停条件

M0-02 与 M0-03 是框架准入门槛。可以并行准备文档、合成资料、静态 UI，但不能把“UI 已做好”当作框架阻塞已解决。无法在一个有效工作日内打通知识库时，记录错误、最小复现与候选替代，走 ADR，不连夜随机换五套数据库。

模型密钥或预算缺失时，可以做契约、纯函数和 fixture 测试；标记 live 测试 BLOCKED。缺少题目审核时，停在 draft；不能让 AI 给自己写一个 reviewer 签名。

五题主链路没通过前：禁止添加语音、跨岗位生成、概率能力估计、自动联网知识核验和多 Agent。M5 必须保留验收时间，不能把“再加一个功能”排在失败测试之前。

## 4. 演示路线：正常路径 + 对照 + 故障

### 主线 A：证明机制真实存在

1. 使用带“演示虚构”标识的嵌入式简历和 JD，上传文本 PDF。展示原文与提取结果，手动纠正一个项目角色描述。
2. 确认资料，展示 Knowledge 入库完成及检索返回的原件/块 ID；不是只展示调用次数。
3. 打开五题覆盖计划：说明其中一题基于用户项目，另一题来自岗位要求。JD 情景题要用“假设”，不能偷换成用户亲身经历。
4. 开始第一题，给出自然但模糊的回答。观察 `PROBE` 和简短理由，追问必须针对本次回答，不按姓名或演示文件 hash 选分支。
5. 回答补充题，再回答其余主问题。展示同一根题只计算一次，充分回答不强制追问。
6. 完成后展示逐题分项、可点击原文、未验证项和优化示例；改写只能复用已有事实。
7. 从报告进入简历工作台，审核一处表达改动后打印。

主线演示所需时间取决于回答和真实模型延迟，不把完整五题假称“一分钟跑完”。短视频可以剪辑等待段，但保留画面标注和实际操作轨迹。

### 对照 B：证明不是写死脚本

保持模型和题库不变，换另一份合成简历，或对同一道题给充分回答。预期应当改变依据/语言或动作，而不是固定追问。展示一个“用户没写 RTOS，系统不会断言他使用过 RTOS”的反例。

### 故障 C：证明可恢复

断开浏览器事件连接并刷新：已接受的答案仍在，页面读取 operation/snapshot 恢复；不多提交一次答案。模拟模型失败时显示暂停/重试，不把预录回答接到 live 会话上。

可另外准备录制回放用于网络故障，但必须标“录制回放”，记录录制版本与日期。回放不计入当场真实调用结果。

## 5. 题面七项要求如何留证

| 题面要求 [S01] | Demo 证据 | 工程映射 |
|---|---|---|
| 简历片段输入 | 合成原件、解析确认页 | R02—R03；T01—T05 |
| 至少五个问题 | 五题计划及实际题目 | R08；T09 |
| 至少一轮追问 | 原回答、Decision、追问和补充回答 | R10；T11、T14 |
| 评分结果 | 根题评价、范围、依据 | R11；T27 |
| 优化后的回答 | 原回答与不添事实的建议 | R12；T28 |
| 工作流图 | 真实注册节点与 Mermaid 图对应 | R19；M0-02、M3-01 |
| LLM 与 Agent 区别 | 状态、检索、策略、恢复和对照 | R19；T06、T21—T25 |

需求编号以 PRD 表为准。施工时如拆分需求，必须同步本映射，不允许长期保留旧编号。

## 6. 给你的项目计划书结构

项目摘要 → 目标用户与问题 → 演示范围 → 工作流与指定框架使用 → 数据与可信边界 → 已实现功能及截图 → 小样本评测 → 成本和部署 → 风险与迭代 → 团队实际分工 → 来源和知识产权说明。

工程规范是“怎么做”，参赛计划书是“为什么值得做、已做到哪、依据是什么”，不要把几十页接口表直接当参赛计划书。所有段落标清：**已验证 / 已实现未验收 / 开发中 / 计划功能**。

如果没有真实用户测试，写“计划开展”，不要写“已服务高校学生”；如果没有国产 OS 运行记录，写“适配验证待完成”；如果只有规则与引用校验，写“降低无依据判断”，不写“保证零幻觉”。

## 7. 发布冻结

发布候选需要保存应用 commit、规范版本、实际依赖锁、模型 ID、提示词版本、题库/资料 hash、测试结果和录制日期。不变更这些条件，结果才具有可比较性。

源码是否上传、计划书页数/格式、视频时长均以学校/系统要求为准；本工程包不编造这些外部限制。
