# 界面与交互规范

当前适用范围：M3-03 P0 比赛 Demo。动态元素与 API 字段的逐项真值表见 [`ui-contract.md`](ui-contract.md)。规划中的简历优化、报告和历史列表没有可读 API，不进入正式 UI。

## 1. 三页主流程

前端只有三个业务路由：

1. `/start`：导入资料、查看真实 Document/Operation 状态、补充并确认候选事实；
2. `/profiles/:profileId/prepare`：输入用户 JD 或明确选择演示 JD，展示 Coverage Map 与五题 Plan；
3. `/interviews/:interviewId`：开始后的当前问题、作答、分析状态、有限追问和本场提问结束。

三页共享“职觉 · AI 面试陪练”页头与三步 Stepper。当前步骤深色，已完成步骤绿色，未完成步骤浅灰；不增加与当前主链无关的导航、工作台或占位入口。

Profile ID 与 Interview ID 可以作为恢复键进入 URL。简历正文、JD 正文、回答正文和服务端绝对路径禁止进入 URL。

## 2. 导入资料页

首屏只强调一个主动作：选择或拖放 PDF。支持文本型 PDF，P0 限制为 10 MiB；隐私说明必须与按钮同屏可见。

选择文件后按真实状态展示：

- 先 `POST /profiles`，再以浏览器管理 boundary 的 multipart 调用 `/profiles/{id}/documents`；
- `queued/running` 显示“文件已接收 / 提取文本 / 索引状态”处理链，并禁用重复上传；
- Operation 终态后重新读取 Document；页数、`extract_status`、`index_status`、warnings 原样映射为产品文案；
- “查看解析文本”打开右侧 Drawer，按 `/documents/{id}/blocks` 的 `page_number` 分页展示；不在浏览器重新解析 PDF；
- `requires_text` 明示文字层不可用，开放手工事实输入，不写“解析成功零项”。

候选事实只能来自 `ProfileView.proposed_claims`。每条可确认或不采用，来源只显示“候选材料/手工补充”等用户可理解标签。解析后候选事实为空时，页面必须明确说明没有结果，不得填演示事实；用户可手工补充，补充后仍保持 proposed，等待本人确认。

只有 `latest_snapshot_id != null` 时显示 `Profile Snapshot Ready` 和“下一步：准备面试”。Document 索引状态不能冒充 Profile Snapshot 门槛。

## 3. 面试准备页

未确认资料直接显示阻断状态和“返回确认资料”，不渲染 JD 表单。

正常准备页提供两种互斥且明确的输入：

- 用户岗位：岗位名称 + JD 正文，调用 `POST /interviews` 时只传 `jd_text/jd_source_name`；客户端不能填写 `source_type`；
- 演示岗位：省略用户 JD 字段，由服务端返回 `jd_source.source_type=synthetic_demo_jd`；页面必须标记“演示岗位材料”。

计划完成后展示：

- 岗位标题、真实 JD 来源和 `jd_requirements[].statement/tier`；
- 左栏 Coverage Map：状态、证据关系和“材料未体现 ≠ 不会”边界；
- 右栏五个 `root_plan.slots` 验证方向；具体问题只在 start operation 成功后读取 `current_question.wording`；
- `competency_id`、priority、reason_code、seed_id、planner/seed bank version 和 limitations 只放在默认折叠的技术明细中。

点击“开始模拟面试”调用 `/interviews/{id}/start`。202 只显示 Operation 处理中；只有 Operation succeeded 且 GET Interview 返回 active 后进入面试页。

## 4. 正式面试页

桌面为“问题与回答 / Evidence Context”左右两栏，窄屏改为单栏。主区只保留当前问题、回答框和当前操作状态，不做聊天气泡或完整历史时间线。

- 顶部进度固定为五个主问题。probe/clarification 仍归属当前主问题，不增加总数；
- 题面严格读取 `current_question.wording/kind/order_index`；
- 主问题右栏显示岗位 requirement、材料验证状态和当前验证方向；
- probe/clarification 右栏显示 `root_results.action/reason_summary/target.followup_intent`；不展示 Observation、Rubric、reference points 或模型私有推理；
- 用户可以明确回答“不知道”，页面不暗示系统已验证真实性或检测造假。

一次“提交回答”创建并保存一组 `client_turn_id + Idempotency-Key`。请求状态不明确或服务端要求稍后重试时，同一次显式重试复用原值；用户选择修改文本才放弃旧命令并创建新标识。

Answer 202 后立即重新 GET Interview，显示服务端 `accepted_answer.raw_text` 与“已保存，正在分析”，输入和重复提交入口隐藏。Operation failed 时保留原回答并显示“重试分析”；重试必须调用 `/operations/{operation_id}/retry`，不得再次 POST answer。

Policy 结果切换必须来自服务端：

- `PROBE` → 补充追问 + Decision Summary；
- `CLARIFY` → 澄清问题 + Decision Summary；
- `NEXT` → 下一个主问题；
- `END` → “本场提问已完成”。

当前 API 没有报告读取端点。结束页不得展示评分、雷达图、优化建议或伪造报告。

## 5. Operation、刷新与错误

SSE 只用于通知刷新；连接关闭不是成功。前端同时轮询 Operation snapshot，终态后重新 GET Profile/Interview。页面切换时关闭旧 EventSource、终止旧 fetch 和 timer，避免迟到响应覆盖当前资源。

当前标签页把不含正文的 operation ID 存入 `sessionStorage`，用于刷新恢复。回答正文只在服务端接受后的 `accepted_answer` 中恢复。失败释放后 API 不再返回 operation ID；同标签页可通过 sessionStorage 重试，跨标签页只能诚实显示“原回答已保存”。

错误必须提供文案而非只靠颜色：

- `SERVICE_NOT_READY`：停用写操作，不自动切 fixture；
- `OPERATION_CAPACITY_LIMITED`：说明队列已满，保留原请求标识供稍后重试；
- `REVISION_CONFLICT`：重新 GET 最新快照，不自动用过期 revision 重放；
- 网络状态不明确：锁定当前文本，提供“使用原请求重试/修改回答”两种明确动作。

## 6. 视觉、响应式与可访问性

视觉采用白/浅灰背景、深蓝主色、克制蓝灰辅助色，绿色只表示成功，橙色表示待处理，红色表示失败。矩形卡片、细边框、小圆角和低阴影为主；禁止 Liquid Glass、大面积渐变、巨型标题、装饰动画和无意义胶囊堆叠。

内容最大宽度约 1180 px。至少检查 390×844、768×900、1440×1000、1920×1080：无横向溢出；长题目、长回答和长岗位要求可换行；两栏在窄屏变单栏。

表单必须有可访问名称，AnyUI Button 支持 Enter/Space，焦点轮廓可见，状态同时包含文字。页面不使用 `innerHTML` 渲染用户输入；文档块与回答均作为文本节点展示。

## 7. 数据与模式标识

`fixture/replay` 必须在页头下方显著说明“不代表真实模型效果”；live 依赖不全时显示 not ready，不能静默回退。页面不显示模型名、API key、token、内部观察 JSON 或服务端路径。

真实简历、真实回答和密钥不得进入 Git、截图、浏览器日志或公开 handoff。视觉验收使用 synthetic PDF/回答；业务文本模型 live 未运行时保持 `NOT_RUN`。
